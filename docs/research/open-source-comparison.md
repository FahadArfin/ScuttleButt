# Open-source comparison

Research date: 2026-08-02. This is an architecture study, not permission to copy implementation code. Licenses change and must be rechecked for the exact commit and file before reuse.

## Executive finding

Matrix plus Synapse is the strongest foundation for Scuttlebutt's federated messaging, identity, rooms, device management, and E2EE requirements. LiveKit is the strongest initial media layer for multi-user voice, video, and screen sharing because it is an open-source WebRTC SFU with self-hosting, simulcast, selective subscription, TURN connectivity, and client E2EE support.

The integration point should follow MatrixRTC discovery and authorization patterns. LiveKit does not provide federation; Matrix supplies room membership and call signaling, while a per-deployment authorization service issues short-lived LiveKit tokens.

## Feature fit by requirement

| Requirement                          | Best reference                    | Phase 0 conclusion                                                                                |
| ------------------------------------ | --------------------------------- | ------------------------------------------------------------------------------------------------- |
| Federated identities and rooms       | Matrix                            | Adopt Matrix; do not create a Scuttlebutt federation protocol.                                    |
| Message E2EE and device verification | Matrix + established Matrix SDKs  | Use maintained crypto bindings and documented recovery/key backup flows.                          |
| Community/server UX                  | Element, Stoat, Mattermost, Zulip | Build Scuttlebutt's own product layer over Matrix spaces/rooms; borrow interaction patterns only. |
| Scalable realtime media              | LiveKit                           | Adopt LiveKit SFU with MatrixRTC-compatible signaling/discovery.                                  |
| Browser screen share                 | LiveKit + WebRTC                  | Start with actual browser capabilities and 1080p30; treat 4K60 as optional.                       |
| TURN traversal                       | Coturn                            | Include Coturn in production guidance and a later local stack.                                    |
| Self-hosting                         | Synapse, LiveKit, Coturn, MinIO   | Keep components separable and document development vs production topology.                        |
| Moderation with E2EE                 | Matrix/Element reporting model    | Use client-assisted reports; never promise server-side inspection of encrypted content.           |

## Licensing conclusions

1. Protocol use is not the same as copying implementation code. Scuttlebutt can implement Matrix APIs and use SDKs without copying Synapse or Element source.
2. Synapse and Element components are AGPL/commercially dual-licensed. If Scuttlebutt links, forks, embeds, or copies any such code, legal review is required.
3. LiveKit, Jitsi, Matrix specification, Zulip, Mumble, and Coturn have permissive or broadly reusable repositories at the project level, but bundled dependencies and SDKs still need license inventory.
4. Rocket.Chat and Mattermost are mixed-license/open-core references; they should be treated as study material, not a source of code.
5. Before Phase 1 creates dependencies, add an automated license report and a human review for copyleft, trademark, codec, and media-provider terms.

## Browser and platform limitations

- Browsers cannot guarantee 4K60 capture, hardware encoding, low latency, or codec availability.
- Browser screen capture requires user permission and may differ for display, window, and tab capture.
- System-audio capture is platform/browser dependent.
- Secure token storage is weaker on the web than in a desktop OS keychain; session design must avoid treating arbitrary browser storage as a secure vault.
- Background audio, global push-to-talk, system tray, deep links, and reliable desktop notifications require a desktop shell and OS permissions.
- Mobile background calls, push delivery, and cryptographic key storage require platform-specific clients and are intentionally deferred.
